Before and after the SQL

Before. Signing in shows the setup notice instead of an error page — the console states plainly that the tables do not exist. No invented numbers, no sample students.

After. The same screens read from students, tests, test_attempts, login_events and audit_log. Existing accounts are backfilled as LP-000001… and the three CSSS tests appear in the registry.

Three steps to switch it on

  1. Paste supabase/APPLY_IN_SUPABASE_EDITOR.sql into the Supabase SQL Editor, after replacing YOUR_EMAIL@example.com with your address. Expected output: tests 3, admin_users 1, students n, attempts 0.
  2. Create that address under Authentication → Users with a password (auto-confirm on).
  3. Open /admin and sign in.

Security notes

  • Authorisation is the admin_users row, checked in the proxy and again in the layout for every page; hiding a link is never the control.
  • RLS: students see only their own profile; admins can read all; audit rows can only be inserted by an active admin for themselves.
  • Export requires an admin session and writes an audit entry with the row count.
  • Sign-in events are written through a definer function, so a client cannot forge another student's event.
