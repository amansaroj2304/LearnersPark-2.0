LearnerSpark 2.0 — Admin Console Audit and Implementation Plan

Prepared: 16 November 2026 · Scope: read-only audit (Steps 1–5 of the brief) · Status: no code or database changes made

1. Executive summary

The repository and live site are verified and connected: amansaroj2304/LearnersPark-2.0 deploys to www.learnssb.online through Vercel, and the Supabase project qozibkbjmtmevrydpqrl backs it.

The platform today is a single-purpose CSSS mock-test app: Google sign-in, three 70-question tests defined in TypeScript, client-side scoring written to one table (test_attempts), and a personal progress page. There is no student profile, no test registry, no administrator, no roles, no audit trail and no server-side score validation.

Three findings shape the plan:

  1. test_attempts is empty (0 rows). There is no historical data to migrate and no data-loss risk — but it also means no production usage yet, so we can design the schema correctly rather than retrofit it.
  2. Scores are computed in the browser and trusted by the server. saveAttempt stores whatever the client sends. This is the most serious integrity gap and must be fixed before an admin console can report trustworthy analytics.
  3. The brief's "one permanent student profile" does not exist yet. Identity is only auth.users (Google), with no mobile number, no student ID and no duplicate detection.

Recommended sequence: schema baseline and backups → server-side scoring and attempt integrity → student profiles with duplicate prevention → admin authentication and roles → dashboard, scorecards, analytics, exports → hardening.

Decisions needed from you before implementation are listed in §9.

3. How the platform works today

  1. Sign-in. LoginButton calls supabase.auth.signInWithOAuth({ provider: "google" }) with redirectTo=/auth/callback?next=…. The callback exchanges the PKCE code and redirects.
  2. Test attempt. /csss/test?test=mock-01 renders a client-side TestRunner. Timing, palette state and answers live entirely in React state.
  3. Scoring. On submit, scoreAttempt() runs in the browser; saveAttempt() (a server action) inserts the computed numbers.
  4. Progress. /progress reads the signed-in user's rows and shows the latest attempt and history. Ranks come from get_test_ranks.
  5. Protection. The proxy redirects unauthenticated users away from /csss/test and /progress.

5. Security findings

  1. Client-trusted scoring (critical). saveAttempt inserts score, correct, accuracy and sections exactly as the browser sends them. Anyone with a session can write an arbitrary attempt. Admin analytics built on this data would be meaningless, and rank manipulation is possible.
  2. No attempt limit enforcement (high). The instructions promise one attempt; Reattempt exists in the runner and the table has no uniqueness constraint.
  3. No rate limiting (high). Sign-in, submission and any future admin endpoints are unthrottled.
  4. No admin separation (critical, by absence). Nothing distinguishes staff from students; any role system must be server-enforced with RLS, not hidden UI.
  5. No audit trail (high). Sensitive reads and edits (exports, status changes) cannot be attributed.
  6. PII surface will grow. Adding mobile numbers and scorecards raises the bar for RLS, export controls and retention.
  7. Positive controls already present. PKCE OAuth, httpOnly cookies, proxy-based route guards, and same-origin redirect validation (open PR #1). test_attempts currently returns 0 rows to anonymous callers, consistent with RLS filtering by auth.uid(); policies should still be reviewed once database access is available.

No student data is exposed today because the table is empty, but the scoring gap must be closed before launch.

6. Proposed architecture

6.1 Data model

-- one permanent profile per auth user
create table public.students (
  id            uuid primary key default gen_random_uuid(),   -- internal
  user_id       uuid unique not null references auth.users(id) on delete cascade,
  student_id    text unique not null,                          -- human ID, e.g. LP-000123
  full_name     text not null,
  email         text not null,
  email_norm    text generated always as (lower(trim(email))) stored,
  mobile        text,
  mobile_norm   text,                                          -- E.164, digits only
  account_status text not null default 'active'
                 check (account_status in ('active','inactive','suspended')),
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);
create unique index students_email_norm_uidx on public.students(email_norm);
create unique index students_mobile_norm_uidx on public.students(mobile_norm)
  where mobile_norm is not null;

-- exam registry (future tests are rows, not code)
create table public.tests (
  id               uuid primary key default gen_random_uuid(),
  test_key         text unique not null,        -- 'mock-01'
  title            text not null,
  category         text not null,               -- 'CSSS', 'OPAM', ...
  description      text,
  exam_date        date,
  duration_minutes int  not null,
  marks_correct    int  not null default 3,
  marks_wrong      int  not null default 1,
  max_marks        int  not null,
  total_questions  int  not null,
  status           text not null default 'draft'
                   check (status in ('draft','published','archived')),
  created_at       timestamptz not null default now()
);

create table public.test_attempts (
  id                  uuid primary key default gen_random_uuid(),
  student_id          uuid not null references public.students(id) on delete restrict,
  test_id             uuid not null references public.tests(id) on delete restrict,
  attempt_number      int  not null default 1,
  started_at          timestamptz not null,
  submitted_at        timestamptz not null default now(),
  time_taken_seconds  int,
  answers             jsonb not null,          -- server-validated responses
  attempted           int  not null,
  correct             int  not null,
  wrong               int  not null,
  unattempted         int  not null,
  score               int  not null,
  max_score           int  not null,
  percentage          numeric(5,2) not null,
  accuracy            numeric(5,2) not null,
  result_status       text not null default 'completed',
  sections            jsonb not null,
  unique (student_id, test_id, attempt_number)
);

create table public.login_events (
  id          bigserial primary key,
  student_id  uuid references public.students(id) on delete cascade,
  event_type  text not null,          -- 'sign_in', 'sign_out', 'failed'
  ip          inet,
  user_agent  text,
  created_at  timestamptz not null default now()
);

create table public.admin_users (
  user_id    uuid primary key references auth.users(id) on delete cascade,
  role       text not null check (role in ('super_admin','admin','read_only')),
  is_active  boolean not null default true,
  created_at timestamptz not null default now()
);

create table public.audit_log (
  id          bigserial primary key,
  admin_id    uuid not null references auth.users(id),
  action      text not null,          -- 'export.students', 'student.deactivate'
  target_type text,
  target_id   text,
  metadata    jsonb,
  ip          inet,
  created_at  timestamptz not null default now()
);

RLS outline

  • students: user may select/update only user_id = auth.uid() (limited columns via a view or column privileges); admins may read all through is_admin().
  • test_attempts: owner-only select; no direct insert from clients — inserts happen only through submit_attempt() (security definer) which recomputes the score server-side.
  • tests: public select where status = 'published'; writes admin-only.
  • login_events, audit_log: admin-only select; inserts via definer functions or triggers.
  • is_admin() is a security definer function reading admin_users, used in every admin policy — never trust the client.

6.2 Identity and duplicate prevention

  • Student identity remains Supabase Auth; one auth.users row = one students row (enforced by unique(user_id)).
  • A database trigger on auth.users insert creates the profile (name/email from the OAuth identity, student_id generated).
  • Mobile is collected in a one-time profile completion step; until then mobile is null.
  • email_norm and mobile_norm are unique where present. If a new identity collides on email but not user_id, or on mobile with a different email, the signup is blocked and queued in a profile_conflicts review table for an administrator — never auto-merged, exactly as the brief requires.
  • Google sign-in normally guarantees one identity per email; the mobile number is where real-world duplicates appear.

6.3 Admin authentication

  • Use Supabase Auth email/password for administrators (the email provider is already enabled), on the same project, with a separate /admin/login screen.
  • Authorisation is the admin_users row, checked server-side in the proxy and again in every admin page, server action and export route. Hiding the button is not a control.
  • Roles: super_admin (everything, including admin management), admin (CRUD on students/tests, exports), read_only (view only).
  • Password reset through Supabase's recovery email; no hashes or tokens ever displayed.
  • Brute-force protection: per-IP and per-account attempt counters (Postgres table or Upstash Redis), progressive delays, optional CAPTCHA after repeated failures; MFA (TOTP) recommended for super_admin.
  • The first administrator is created by a one-off script run with the service-role key from a trusted machine, or by seeding admin_users for your email and using the normal password reset. No credentials in code.

6.4 Server-side scoring

Replace the client-computed insert with a single RPC:

  1. Client submits { test_key, answers, started_at, submitted_at }.
  2. submit_attempt() loads the authoritative question bank (from questions table or a signed server module), validates every answer index, computes correct/wrong/score/accuracy/sections, enforces attempt policy and duration, writes the row and returns the result.
  3. The client renders the returned result; /progress reads stored values only.

This also produces the data the scorecards and analytics need (per-section, time taken, unattempted).

6.5 Test registry

Move test metadata into tests and question data into questions (or keep question banks as versioned JSON in the repo and register metadata in the DB). New tests become rows — no dashboard code changes, satisfying "future tests automatically appear".
